# Review 1 (Home Assistant version)

> Code review findings (all fixed at the time). Kept as a record.

_Workflow: Review the wall-panel repo on given dimensions, then adversarially verify every finding_

- **[major] novice-journey:** The Octopus guide says the extras package finds the Octopus entities automatically, so the user doesn't have to type them anywhere. It also says the panel needs a 'cheapest slot' sensor from the package. Neither is true. The package has no Octopus sensors: it holds only the five Fully Kiosk automations, and the cheapest slot is worked out in the price card's JavaScript. This contradicts dashboard.md line 34 and the settings block in wall-panel.yaml, which both tell the user to replace the example serial_MPAN by hand. A novice who reads octopus.md first (README step 2 comes before step 3) will skip that edit, because the guide said it wasn't needed. They will also think the 'optional' package is required. (docs/integrations/octopus.md) → 
- **[major] novice-journey:** Read literally, the reuse shortcut skips the only step that adds the integration to Home Assistant. Step 4 is 'Home Assistant → Add integration → Google Calendar'. A user who set up Nest first (the README lists Nest first, and this sentence encourages it) enables the Calendar API, jumps to step 5 and finds no `calendar.` entities. (docs/integrations/google-calendar.md) → 
- **[major] novice-journey:** The Nest guide warns that the OAuth client secret can't be viewed again, but it never says to save it. The Google Calendar guide then tells the user to reuse this same client. Home Assistant stores application credentials per integration, so adding Google Calendar asks for the Client ID and secret again. A novice who copied the secret straight into the Nest dialog is stuck at Calendar step 4, and neither guide explains how to recover. (docs/integrations/nest.md) → 
- **[major] novice-journey:** `kiosk_mode: {kiosk: true}` applies to every user, including the admin who pastes the dashboard on a PC. After saving and reloading, the header (with the pencil and ⋮ menus) and the sidebar disappear on that dashboard everywhere. The admin is then stuck on it whenever they click 'Wall panel' in the sidebar. Option B's 'open the dashboard → ⋮ → Refresh' is also impossible, because ⋮ is hidden. The docs mention `?disable_km` only as something to do on the tablet, so a novice who needs to fix a typo has no visible way back to the editor or to Settings. (homeassistant/dashboard/wall-panel.yaml) → 
- **[minor] novice-journey:** The guides tell the user to edit the dashboard on the tablet with `?disable_km`, but the tablet is logged in as the `panel` user, which home-assistant.md deliberately creates without Administrator rights. Non-admin users can't edit dashboards, so the user sees menus but no pencil. (docs/tablet.md) → 
- **[major] novice-journey:** The Kia integration is optional, and many users will skip it. The advice to 'delete the e-Niro tile' breaks the file for them. The tile is defined once with a YAML anchor (`&tile_car`, lines 239-249) and reused by an alias in the compact grid (line 270). Deleting only the visible tile definition leaves `*tile_car` pointing at nothing, and the Raw configuration editor refuses to save with an unknown-alias error. The 'button that opens the Kia app' alternative gives no snippet or package name, which a novice can't write. (docs/dashboard.md) → 
- **[major] novice-journey:** The table tells users whose network doesn't resolve `homeassistant.local` to put the HA box's IP in the Start URL (line 51). Three rows later, the URL whitelist allows only `http://homeassistant.local:8123/*`. A novice who follows both rows gets their own dashboard blocked by the whitelist. Troubleshooting (line 28) admits the whitelist must match, but setup never says so. The advice also doesn't help if the IP changes: nothing tells the user to reserve it. (docs/tablet.md) → 
- **[major] novice-journey:** The camera is the brief's first display requirement, and there is no fallback when it isn't available. The 2025 Nest Cam Indoor (3rd gen) is the current model a UK buyer is likely to own, and it is listed as reported not exposed by the API, with panel behaviour 'none'. The same applies when the user decides not to go through the Google Cloud and US$5 route. In both cases the largest tile shows an entity error and the docs offer no alternative. (docs/integrations/nest.md) → 
- **[minor] novice-journey:** Five places point the user to 'Settings → Entities', which doesn't exist in HA 2026.9's Settings menu. Entities are a tab under Devices & services. Every entity-ID lookup is written this way, and it is the step a novice does most. (docs/dashboard.md) → 
- **[minor] novice-journey:** The guide says to open `wall-panel.yaml` in a text editor, but never says how to get the file off GitHub. A novice reading the repo in a browser has no local copy and no text-editor habit. Pasting first and editing the settings block inside the Raw configuration editor before pressing Save avoids both problems. It is equivalent, because anchors are expanded only on save. (docs/dashboard.md) → 
- **[minor] novice-journey:** The table implies Claude voice mode is voice-launchable ("Hey Google, open Claude"), but voice-and-apps.md says this only opens the app and the user must then tap the voice icon. The requirement is partly met, and the README should say so. (README.md) → 
- **[minor] novice-journey:** The extras package is the only step with no guide. The README links straight to a YAML file, and the install steps are YAML comments. They tell the user to edit configuration.yaml and create /config/packages, but say nothing about what to do if a `homeassistant:` key already exists, how to create a folder in File editor, or to check the configuration before restarting. The step 6 summary also leaves out the two automations that matter most for 'dashboard open most of the time': back to the dashboard after 10 minutes, and dim at night. (README.md) → 
- **[minor] novice-journey:** The setup table never turns on Fully's fullscreen mode, but troubleshooting relies on it being on. Following the table literally leaves Android's status and navigation bars on screen, which squeezes the 1280×800 layout and looks unfinished on a wall panel. (docs/tablet.md) → 
- **[minor] novice-journey:** Prerequisites only come up partway through the steps, and core jargon is never defined. The free GitHub account HACS needs is mentioned only at the end of HACS step 3. The card for Google's US$5 payment, the Octopus API key, the Kia login, Spotify Premium and a PC for the Google Cloud console are never gathered up front. 'HACS', 'integration', 'entity'/'entity ID', 'YAML' and 'package' are used as if the reader already knows them. (README.md) → 
- **[nit] novice-journey:** The comment says the serial_MPAN appears in six lines. There are five Octopus lines (26-30), so a careful novice will go looking for a sixth. (homeassistant/dashboard/wall-panel.yaml) → 
- **[nit] novice-journey:** The guide says the chart copes with any slot length, including 15-minute slots. That overstates it. The chart hard-codes a +15 min shift to centre bars on half-hour slots, so 15-minute slots would be drawn one slot late. The integration also splits every tariff into 30-minute increments. (docs/integrations/octopus.md) → 
- **[nit] novice-journey:** Adding other household members' voices from their own phones or accounts is a Google Home (Nest speaker) household feature. On an Android tablet, Voice Match belongs to the signed-in account, so a novice will look for an 'add person' option that isn't there. (docs/voice-and-apps.md) → 
- **[major] security:** The guide suggests that leaving the Kia PIN blank keeps Home Assistant read-only. On a 2021 e-Niro that is false. The integration always creates a door-lock entity, and on older (non-CCS2) cars unlock, charge start/stop and climate start are sent without the PIN. Home Assistant has no per-entity permissions, so any HA login can unlock the car, including the tablet's non-admin `panel` user. The integration also creates a GPS `device_tracker` for the car that every HA user can see on the map. The doc only says 'Don't put lock/unlock or climate controls on a wall panel', but the entities still exist and appear on the auto-generated Overview dashboard. (docs/integrations/kia.md) → 
- **[major] security:** The setup leaves the tablet permanently unlocked. Screen lock is None, Fully's kiosk mode is off so its settings open with a swipe, and a Home button drops anyone to the Android app drawer. Yet the docs never say which accounts to sign in on it. Users will naturally use their personal Google account, which puts Gmail, Photos, Drive, the Google Home app (cameras and locks), Chrome saved passwords and Gemini's personal results in reach of any visitor or tradesperson. The same goes for their personal Claude account: full chat history, projects and memory. home-assistant.md then says a non-admin HA user means 'a visitor poking at it can't change settings', which overstates the protection. (docs/tablet.md) → 
- **[major] security:** The guide turns on camera-based motion detection and Remote Admin, then adds the Fully integration. It never mentions that this turns the tablet's front camera into a camera that other people can view. Fully's Remote Admin serves camera snapshots ('camshot') and screenshots by default, over plain HTTP on port 2323, with the password in the query string. The HA Fully Kiosk integration automatically creates `camera.wall_panel` (the front camera, working because motion detection is on) and `image.wall_panel_screenshot` (whatever app is on screen, e.g. Claude or Keep). Both are enabled by default and visible to every HA user and device, and from outside the home if remote access is ever turned on. None of the panel's automations need either entity. (docs/tablet.md) → 
- **[major] security:** The whitelist is hard-coded to `http://homeassistant.local:8123/*`, but the same table (and dashboard.md) tells users to switch the Start URL to the HA box's IP if the .local name doesn't resolve. Anyone who follows that fallback gets a whitelist that blocks their own start URL, so the panel doesn't load. The obvious workaround is to clear the whitelist, which leaves the JavaScript Interface open to any page. The same thing happens if they later serve HA over https, which voice-and-apps.md suggests for the microphone. troubleshooting.md line 112 only hints at this ('it must include your Home Assistant address'). (docs/tablet.md) → 
- **[minor] security:** The panel only reads the calendar, but the integration always links read/write first. Read/write lets any Home Assistant user, including the tablet's non-admin `panel` user, create and delete events in your Google Calendar through HA. The doc presents read-only as an optional toggle and leaves out the next step: switching to read-only makes the integration fail until you re-authenticate. A user who flips the option sees the calendar go unavailable and will probably switch it back. (docs/integrations/google-calendar.md) → 
- **[minor] security:** The preview HA listens on all network interfaces, not just localhost. It uses credentials published in the repo (`panel` / `panelpass123`), and that user is an administrator, not the non-admin user the real guide prescribes. While the preview runs, anyone on the same Wi-Fi (e.g. a café or office) can log in as admin. The README and run.sh say '127.0.0.1:8123', which implies local-only. Because the preview user is an admin, screenshots and button tests also don't reflect what the real non-admin tablet user sees. (dev/preview/config/configuration.yaml) → 
- **[minor] security:** The docs say to add `?disable_km` on the tablet 'to edit' the dashboard. The tablet is logged in as the non-admin `panel` user, and HA only lets admins edit dashboards, so this can't work. The likely result is that the user logs Fully in with their admin account to make the edit, and Fully remembers that login, leaving an admin session on an unlocked wall tablet. (docs/tablet.md) → 
- **[minor] security:** The tablet account's username is the predictable `panel`, and the guide gives no advice on its password and doesn't turn on HA's 'Local access only'. Any HA user can operate every entity, including cameras, the thermostat, the Kia controls and the Fully tablet. The docs also nudge users toward HTTPS (voice-and-apps.md 93-94), which often means remote access. If that happens, this account becomes an internet-facing login that doesn't need to be. (docs/home-assistant.md) → 
- **[minor] security:** The section says Claude, via HA Assist, 'can also see and control your Home Assistant devices', but never tells the user to review what is exposed. HA exposes new climate, cover and switch entities to Assist by default. With the Kia integration that includes the car's climate, the EV charging and climate switches, and window covers. A misheard request at the wall panel could then start the car's climate or stop charging. (docs/voice-and-apps.md) → 
- **[nit] security:** The docs tell users to turn on USB debugging for the adb tests but never say to turn it off afterwards. On an always-unlocked wall tablet, anyone with a cable can accept the ADB prompt and get a full shell. (docs/voice-and-apps.md) →
