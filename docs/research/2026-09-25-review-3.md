# Review 3 (Home Assistant version)

> Code review findings (all fixed at the time). Kept as a record.

_Workflow: Review the wall-panel repo on given dimensions, then adversarially verify every finding_

- **[major] package-harness:** The nightly refresh never runs on a new install. has_value() returns false for the state 'unknown', and a button entity stays 'unknown' until it has been pressed once. This automation is the only thing that presses button.wall_panel_load_start_url, so its own condition blocks it forever. The docs point users to this refresh as the fix for a sluggish tablet and a frozen camera (troubleshooting.md lines 13 and 21, nest.md lines 87-88). (homeassistant/packages/wall_panel.yaml) → 
- **[major] package-harness:** 'Dim at night' never runs with Fully's default settings. By default Fully's screenBrightness setting is an empty string, which means 'use system brightness'. The HA number entity then reports None, so its state is 'unknown' and has_value('number.wall_panel_screen_brightness') is false. The automation can't set a first value because its own condition blocks it. docs/tablet.md never tells the user to set Fully's Screen brightness. (homeassistant/packages/wall_panel.yaml) → 
- **[major] package-harness:** A numeric_state trigger only fires when the value crosses the threshold. If the battery is already below 30% (or above 80%) when the automation starts up, for example after an HA restart or update, an automation reload, or a battery that fell below 30 while HA was down, nothing fires until the level first moves back inside the range. With the plug off, the tablet can't get back above 30% by itself, so it drains to 0. The same happens if the plug is unavailable at the moment of the crossing: the has_value condition fails and nothing retries. The mock's own starting state (battery 85%, charger on) is this case. The test hides it by moving to 50% first. (homeassistant/packages/wall_panel.yaml) → 
- **[major] package-harness:** The doc describes package features that don't exist. It says the package 'finds these entities automatically, so you normally don't have to type them anywhere' and mentions a 'cheapest slot' sensor in the package. homeassistant/packages/wall_panel.yaml contains only five Fully Kiosk automations, with no template sensors and nothing about Octopus. The dashboard needs the IDs typed by hand (wall-panel.yaml lines 16-30), so a user who believes this doc will skip that step and get broken energy cards. (docs/integrations/octopus.md) → 
- **[major] package-harness:** On a fresh clone the package never reaches the preview. config/packages/ is gitignored, and neither setup.sh nor run.sh creates it. `cp … config/packages/wall_panel.yaml 2>/dev/null || true` therefore fails silently, HA starts without the automations, and test_package.py reports 5 FAILs and then crashes with KeyError at line 51 (`by_id["wall_panel_nightly_refresh"]`). It only works in this workspace because someone created the directory by hand. (dev/preview/run.sh) → 
- **[minor] package-harness:** The package test never evaluates the automations' conditions, and it doesn't cover the edge cases where the package fails. automation.trigger skips conditions by default, so the has_value bugs (package-harness-1/2) pass. The charger test never starts from the 'already past the threshold' state (package-harness-3). The back-to-dashboard automation isn't tested at all. (dev/preview/test_package.py) → 
- **[minor] package-harness:** `not_from: unavailable` still matches an old_state of None. When the Nest integration is reloaded or re-authenticated, or finishes setting up after HA has started, the event entity is re-added with its restored last event. If that event was 'ring' or 'camera_person', the panel wakes with no doorbell. When the entity is removed (to_state None), the condition throws a template error into the log. (homeassistant/packages/wall_panel.yaml) → 
- **[minor] package-harness:** Fully's 'Keep screen on' only applies while Fully's window is in front. After the user taps Home/Spotify/Claude and walks away, Android's own screen timeout turns the screen off long before the 10 minutes are up. Bring-to-foreground, or turning the screensaver off on a doorbell ring, doesn't switch the screen back on. The docs don't enable Fully's 'Turn screen on on motion', so the panel stays black until someone presses the power button. (homeassistant/packages/wall_panel.yaml) → 
- **[minor] package-harness:** Both 'back to the dashboard' and 'wake on doorbell' press Fully's Bring to foreground while another app is in front. Android 10+ blocks background apps from starting activities unless the app has the 'Display over other apps' permission. The guide never tells the user to grant it to Fully, and Kiosk mode is OFF, which is the usual prompt for it. So the press can do nothing without any error. The project's own research flagged this, but it didn't make it into the docs. (docs/tablet.md) → 
- **[minor] package-harness:** HA 2026.9.3 needs Python >=3.14.2, but setup asks uv for any 3.14 and the README says uv 0.9 is enough. uv 0.9.0-0.9.15 can only download 3.14.0 or 3.14.1, and uv also prefers an existing system 3.14.0/3.14.1. In either case `uv pip install homeassistant==2026.9.3` fails. The next run of setup.sh skips venv creation (`[ -d .venv ] ||`), so the broken venv stays until the user deletes it by hand. (dev/preview/setup.sh) → 
- **[minor] package-harness:** The restart logic is racy and never reports failure. After `kill`, it waits a fixed 4 s, but HA shutdown often takes longer. The new instance then exits with 'Another Home Assistant instance is already running' (.ha_run.lock) or can't bind port 8123, while the old, still-stopping instance may answer the health check. If HA never comes up, the loop runs for 6 minutes and still prints ' up: …' with exit status 0. (dev/preview/run.sh) → 
- **[minor] package-harness:** The preview HA listens on every network interface (HA's default). Its login is an administrator account whose password, panel/panelpass123, is published in README.md and setup.sh. Anyone on the developer's LAN can log in as admin while the preview is running. (dev/preview/config/configuration.yaml) → 
- **[minor] package-harness:** The README says the preview renders the dashboard 'exactly as the tablet would', but two differences hide real-world behaviour. (1) The preview user 'panel' is an admin, while docs/home-assistant.md section 5 makes the tablet's 'panel' user a non-admin. (2) The mock camera has no STREAM feature, so the frontend uses MJPEG instead of the WebRTC player a Nest camera uses. Problems that only show up for non-admin users or in the WebRTC player can't appear in the preview. (dev/preview/README.md) → 
- **[nit] package-harness:** The comment says the automation acts when someone 'walks away', but it simply fires 10 minutes after the foreground app last changed, even mid-use (e.g. a long Claude voice chat or a video). It also never fires if the tablet is already in another app when HA restarts or the automation is reloaded, because the state-trigger timer starts only on a change seen after it attaches. (homeassistant/packages/wall_panel.yaml) → 
- **[nit] package-harness:** gettoken.sh calls the system `python3`, although the harness otherwise relies only on the uv-managed venv. The README doesn't list python3 as a requirement. On macOS without the Command Line Tools, or on a minimal Linux install, it fails, and screenshot.js, test_buttons.js and test_package.py all depend on it. (dev/preview/gettoken.sh) → 
- **[nit] package-harness:** The mock registers panel_mock.fire_event without a services.yaml, so every start logs an ERROR. The mock Agile 'current rate' and the today/tomorrow rate lists are computed once at startup, so after 30 minutes 'Price now' no longer matches the chart's current slot, and after midnight 'today' shows yesterday. (dev/preview/config/custom_components/panel_mock/event.py) → 
- **[nit] package-harness:** The README doesn't mention test_package.py or test_buttons.js. test_buttons.js asserts nothing: it prints the calls and always exits 0, so a broken launcher still 'passes'. The setup.sh comment points to docs/dashboard.md for the tested card versions, but that doc lists no versions. The extra pip packages (home-assistant-frontend, hassil, …) are unpinned, while HA 2026.9.3 pins e.g. home-assistant-frontend==20260826.7. (dev/preview/README.md) → 
- **[major] docs-integrations:** The doc says the package finds the Octopus entities by itself, so the user normally doesn't need to type them anywhere. That is false. homeassistant/packages/wall_panel.yaml contains no Octopus logic at all; it only has Fully Kiosk automations. The dashboard only works once the user replaces the example serial_MPAN in the settings block by hand. A user who follows octopus.md will skip that step, and the price, chart and usage tiles will point at non-existent entities. (docs/integrations/octopus.md) → 
- **[major] docs-integrations:** 'Enable the Calendar API (step 1) and skip steps 2–4' also skips step 4, which is adding the Google Calendar integration in Home Assistant. Someone who follows this literally never adds the integration. Even when step 4 is done, HA stores OAuth application credentials per integration domain, so Google Calendar asks for the Client ID and Client secret again. nest.md:45 warns that the secret can't be viewed again, and nothing tells the user to keep a copy. Reuse therefore fails unless they saved it. (docs/integrations/google-calendar.md) → 
- **[minor] docs-integrations:** The doc refers to a display-only "cheapest slot" sensor in the package. No such sensor exists. The package has no template sensors, and the dashboard works out 'cheapest ahead' in the price card's button-card JavaScript. Users will look for a sensor that isn't there. (docs/integrations/octopus.md) → 
- **[minor] docs-integrations:** The claim that the chart 'will cope if Octopus ever moves to 15-minute slots' is wrong. The BottlecapDave integration splits every tariff into 30-minute slots in code, so 15-minute Agile data would need an integration update first. The dashboard chart also hard-codes a +15 min offset that only centres 30-minute bars. (docs/integrations/octopus.md) → 
- **[minor] docs-integrations:** 'Tested against v19.x' claims more than the evidence supports. The repo's only test harness uses mock entities that copy the integration's entity IDs. Nothing was run against the real BottlecapDave integration or a live Octopus account. (docs/integrations/octopus.md) → 
- **[minor] docs-integrations:** 'Tap the tile to see the "Last updated" time' is misleading. The more-info dialog shows when Home Assistant last saw the battery value change, and that time resets on a restart. It is not when the car last uploaded data. With cached polling the value often stays the same for hours while the car's upload time moves on, or the reverse. The integration has a dedicated sensor for the car's own timestamp. (docs/integrations/kia.md) → 
- **[minor] docs-integrations:** The 200 calls/day EU quota is stated as fact, but it is a community figure, and reports disagree on whether cached reads count. The '144' figure is also unexplained: 30-minute polling is 48 polls a day, so readers can't reconcile the two numbers. The figure only works because each cached poll makes about 3 API calls on an e-Niro. (docs/integrations/kia.md) → 
- **[minor] docs-integrations:** The doc implies Met.no always exists, and that a wrong or default location only gives the wrong place's weather, fixable in General settings. In fact, if onboarding finished with the default (Amsterdam) coordinates, Home Assistant never creates the Met.no entry. `weather.forecast_home` does not exist, and fixing the location later does not create it. (docs/integrations/weather.md) → 
- **[minor] docs-integrations:** 'Settings → Entities' isn't an item in HA 2026.9's Settings menu. Entities is a tab under Settings → Devices & services, so a new user following the path won't find it. The same path appears in docs/dashboard.md:25 and in the comment at wall-panel.yaml:15. (docs/integrations/octopus.md) → 
- **[minor] docs-integrations:** The row says the Claude button opens Claude's voice screen and lists 'Hey Google, open Claude' as the voice launch. Both claim more than the evidence shows. The entry point is an undocumented activity taken from a decompiled manifest and hasn't been tested on a device. The voice command only opens the app, not voice mode, as docs/voice-and-apps.md:77 itself says. The brief specifically asked for voice launch of Claude voice mode. (README.md) → 
- **[minor] docs-integrations:** The table flags the 2025 Nest Cam Indoor (wired, 3rd gen) but leaves out the other 2025 '2K' model, the Nest Cam Outdoor (wired, 2nd gen). Its SDM support is also unconfirmed. The section exists so the user checks before paying the non-refundable $5. (docs/integrations/nest.md) → 
- **[nit] docs-integrations:** 'A steady 1–2 Mbps' and the '(1–3 s)' restart time are stated as fact, but they are unmeasured estimates. The source research explicitly marked the bitrate UNVERIFIED. It also left open whether an 'another app in front' or Fully screensaver state actually sets document.hidden in the WebView. (docs/integrations/nest.md) → 
- **[nit] docs-integrations:** 'You can set calendar access to read-only in the integration's options' leaves out that changing it makes the integration fail with 'reauth required'. The existing token has the read/write `calendar` scope, not `calendar.readonly`, so the user has to sign in again. (docs/integrations/google-calendar.md) → 
- **[nit] docs-integrations:** The table says the panel uses today's kWh (`current_accumulative_consumption`), but the dashboard only shows today's cost. There is no kWh tile and no settings key for it. (docs/integrations/octopus.md) →
